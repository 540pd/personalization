02Why is ontology useful?

Its value is not the diagram itself. Its value is that systems and people can reuse the same meaning across data, decisions, analytics, governance, and AI agents.29

See the difference

The underlying data may be similar; the difference is whether meaning is explicit and reusable.

Business language fragments

  • CRM says Customer, commerce says Shopper, loyalty says Member.
  • Product and SKU are used interchangeably even when pack size matters.
  • Every dashboard recreates category and channel mappings.
  • An AI agent guesses what “eligible product” means.

Implementation becomes brittle

  • Joins depend on undocumented IDs and one-off lookup tables.
  • Rules are scattered across pipelines and applications.
  • Numbers do not reconcile because definitions differ.
  • Change requires manual impact analysis across systems.

Meaning becomes shared

  • Customer, Shopper, and Member are mapped or distinguished explicitly.
  • Product, SKU, pack, and assortment have clear roles.
  • Business definitions, aliases, and context are reusable.
  • Agents can resolve intent through defined relationships.

Implementation becomes governable

  • Canonical IDs and source mappings are documented.
  • Rules and ownership are visible and testable.
  • Metrics reuse consistent definitions.
  • Change impact can be traced through relationships and consumers.

Six kinds of value

Filter the cards by the part of the project you are working on.

⌘

Connect systems by meaning

Map different names, IDs, and structures to shared concepts and relationships.

Solves: brittle cross-system joins and duplicate mapping.
▦

Make metrics comparable

Reuse the same definitions of Product, Market, Channel, Customer, and Promotion.

Solves: dashboards that disagree because their dimensions differ.
⌁

Improve semantic retrieval

Retrieve through relationships such as Brand → SKU → Promotion → Retailer, not keywords alone.

Solves: missed context and weak multi-hop retrieval.
✓

Validate agent actions

Check whether a proposed action is semantically valid before an agent executes it.

Solves: syntactically valid but business-invalid tool calls.
◎

Expose ownership and provenance

Record who owns a concept, which source supports a fact, and when it changed.

Solves: unresolved conflicts and silent definition drift.
↻

Reuse domain knowledge

Keep meaning separate from one application so multiple products can consume it.

Solves: rebuilding the same domain logic in every solution.

Example: a promotion agent

A user asks an agent to create a 20% promotion for all Dove shampoo products at Retailer A.59

1 · Interpret

Understand intent

The LLM identifies Brand, product category, retailer, discount, and requested action.

2 · Resolve

Find eligible SKUs

The ontology guides the path Brand → Product → SKU and Retailer → carries → SKU.

3 · Validate

Check business rules

Confirm discount limits, dates, market, approvals, and conflicting promotions.

4 · Execute

Create only valid actions

The agent invokes tools after semantic and policy checks, with an audit trail.

03What is inside an ontology?

The labels are easy. The real design work is deciding which things deserve to be concepts, which are actual facts, and which relationships and rules matter.245

Building block 1

Classes / concepts

The kinds of things that exist in the domain. Classes form the reusable vocabulary.

CPG examplesProduct, SKU, Brand, Retailer, Promotion, Market
Question answeredWhat kind of thing is this?
Hierarchy exampleShampoo is a type of Hair Care Product
Common mistakeTurning every field into a class
Building block 2

Instances

Specific, identifiable examples of classes—the facts that populate the model.

CPG examplesDove; Retailer A; SKU-204; Promotion P-311
Question answeredWhich actual thing are we talking about?
Identity exampleSKU-204 may be identified by a GTIN
Common mistakeConfusing “Shampoo” with one specific shampoo SKU
Building block 3

Relationships

Named, directional connections that make meaning traversable.

CPG examplesSKU belongsTo Brand; Retailer sells SKU
Question answeredHow can two concepts connect?
Design noteUse precise verbs and define direction
Common mistakeUsing vague edges such as “related to”
Building block 4

Properties

Descriptive values attached to a thing or sometimes to a relationship.

CPG examplesnetContent, discountPercent, startDate, GTIN
Question answeredWhat describes this concept or fact?
Datatype examplediscountPercent is numeric
Common mistakeEncoding a relationship as ungoverned text
Building block 5

Constraints

Rules that state what is valid, required, permitted, or impossible.

CPG examplesendDate follows startDate; one SKU has one primary GTIN
Question answeredWhat must be true?
Agent valueReject a business-invalid action before execution
Common mistakeAssuming OWL alone replaces all operational validation
Building block 6

Context, provenance, and governance

Meaning often depends on source, market, time, owner, consent, and alternative vocabulary.

CPG examplesmarket applicability, source system, steward, synonym
Question answeredWhere, when, for whom, and according to whom?
Evidence exampleA relationship is supported by POS data for a date range
Common mistakeAdding provenance and consent after deployment

Read one statement precisely

A semantic statement is easiest to read as Subject → Relationship → Object, with properties and constraints around it.

Subject

Promotion P-311

A specific instance of the class Promotion.

Relationship

appliesTo

A semantic connection from a Promotion to an eligible SKU.

Object

SKU-204

A specific SKU representing Dove Shampoo 180 ml.

Properties

discount = 20% · startDate · endDate

Values attached to the promotion or relationship.

Constraint

endDate must follow startDate

A rule that lets a system reject an invalid fact or action.

Structure versus evidence

A useful ontology contains both, but they should not be created in the same way.

Author cheaply

Structure

What things are and how they relate. Draft during discovery as a testable hypothesis.

  • Entity set and hierarchy
  • Core relationships—the spine
  • Canonical identifiers and reconciliation rules
  • Alignment with external standards
Earn empirically

Content and weights

How often, how strongly, for whom, and in which context. Estimate from real signal.

  • Aliases and synonym coverage
  • Relationship strengths or affinities
  • Market, channel, culture, and lifecycle context
  • Recency, emergence, and change over time

04How do you build an ontology?

Discover first. Model second. Validate continuously. A useful ontology is distilled from business decisions, domain expertise, systems, standards, constraints, and evidence.12

Step 1

Start with decisions and competency questions

Define what people or systems must decide, retrieve, validate, or automate. This controls scope and granularity.

Output

A short list of questions the ontology-enabled solution must answer.

Which SKUs are eligible for this promotion?
Which products are sold by this retailer in this market?
Which promotions conflict in date, channel, or audience?
Step 2

Discover the domain through multiple lenses

Read the business, catalog, data, systems, users, experts, standards, workflows, KPIs, time, privacy, governance, and technical constraints.

Output

A domain term inventory, decision map, source inventory, ownership view, and list of open ambiguities.

Which terms do domain experts use informally?
Where do source IDs collide or diverge?
Which relationships are observed versus merely desired?
Step 3

Sketch a level-1 ontology—the spine

Model the few concepts and relationships required by the competency questions. Keep it explainable and easy to change.

Output

A one-page concept-and-relationship model with definitions and examples.

Can every node justify itself through a decision?
Are Product, SKU, Pack, Brand, and Category separated clearly?
Are relationships directional and unambiguous?
Step 4

Map systems, identifiers, aliases, and standards

Connect each concept to source fields, canonical keys, alternative names, owners, and applicable external vocabularies such as GS1.678

Output

A mapping specification explaining how source data becomes canonical concepts and relationships.

Which key identifies the same entity across systems?
Which terms are true synonyms—and which are only similar?
Which industry definitions should be reused?
Step 5

Populate, test, and let the data disagree

Use representative and then scaled data to expose missing concepts, impossible links, poor coverage, unexpected aliases, and context effects.

Output

A corrected ontology, coverage metrics, validation rules, and a prioritised gap list.

Can the model answer the original questions with real records?
Which expected relationships cannot be populated?
Which affinities must be estimated rather than asserted?
Step 6

Assign ownership and a change process

Ontology is a maintained product. Define who owns each domain, approves changes, handles conflicts, versions releases, and checks downstream impact.

Output

Named stewards, review cadence, versioning rules, issue workflow, and adoption measures.

Who arbitrates conflicting definitions?
How are breaking changes communicated?
Which teams and applications consume the ontology?

What maturity actually means

Maturity is not simply more nodes. It is more of the model being supported, populated, and contextualised by evidence.1

Level 1

The spine

A small structural hypothesis: core concepts, hierarchy, relationships, IDs, and definitions.

Level 2

Filled and aliased

Real data populates the model, corrects edges, and adds vocabulary, synonyms, and provenance.

Level 3

Weighted and contextual

Relationships gain evidence-backed strength, market applicability, recency, and temporal dynamics.

Failure modes to avoid

Each usually signals that a discovery lens or governance step was skipped.1

⚠ Museum ontology

A polished graph that no real decision, query, or workflow consumes.

⚠ Vocabulary fragmentation

Each pipeline invents its own terms, so reports and systems cannot reconcile.

⚠ Whiteboard weights

Affinity or applicability is guessed instead of estimated from signal.

⚠ Retrofit consent

Privacy, source, and permissible use are added after the model is operational.

⚠ Bolted-on time

History, seasonality, lifecycle, and changing relationships are discovered too late.

⚠ Ontology rot

No owner or release process exists, so definitions drift while consumers keep using them.

The line to remember

Discovery creates understanding; ontology compresses it into a shared contract.1

Author the first structure cheaply from qualitative discovery. Let real data fill it, challenge it, and earn detailed vocabulary, context, and weights.

The ontology is the contract; data is what fills and corrects it. A good first version is small, useful, testable, and owned.
